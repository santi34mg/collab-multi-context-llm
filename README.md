# Collaborative Multi-Context Model — Rust prototype

A Rust research implementation of the architecture in [DESIGN.md](DESIGN.md): a shared-weight model with multiple generation streams, structured context visibility, peer-context edits, and persistent memory contexts. Includes optional in-process GGUF inference and knowledge distillation from the locally installed Qwen3.5 and LFM2.5 teachers.

**The collaborative model is an executable reference prototype, not a pretrained LLM.** Its tiny transformer is fully trainable. Separately, the optional native backend runs pretrained GGUF teachers through llama.cpp's C library, and their final answers can train the student. This does not yet establish that the collaborative architecture improves general reasoning.

## Local Qwen / LFM inference and distillation

See **[the inference and distillation guide](docs/INFERENCE.md)** for the tested native setup and complete workflow:

```sh
# After building with the native feature and compatible llama.cpp libraries:
./target/release/agent-collab infer --preset qwen -p 'What is 2 + 2?' -n 64
./target/release/agent-collab infer --preset lfm -p 'What is 2 + 2?' -n 256

# Or use an already-running local helper without the native build feature:
cargo run --release -- distill --endpoint http://127.0.0.1:8080 --input examples/distillation-prompts.json --output target/teacher.jsonl -n 512
cargo run --release -- train-distill --input target/teacher.jsonl --epochs 10 --output target/student.json
```

Teacher collection is sequence-level distillation, not RL or logit transfer. GGUF weights remain frozen; only the separate Rust student is trained.

## Quick start

Requires a Rust toolchain supporting edition 2024. Default Rust dependencies are `serde` and `serde_json`; the existing student/demo/tests need no Python, GPU, model downloads, or API keys. Native GGUF inference additionally requires the compatible llama.cpp libraries, a C compiler, and local model weights.

```sh
cargo test
cargo run --release -- demo
cargo run --release -- train
```

### 1. Collaboration and persistence demo

```sh
cargo run --release -- demo memory.json trace.json
```

Two scripted streams publish private arithmetic clues. One proposes an edit to the other's working entry; the owner accepts it. A selected result is staged for memory, both streams finish, and the engine commits and saves the memory. The demo then reopens the file into a fresh session and retrieves the result.

All operations travel through the same **one-byte-per-stream-per-round** decoding interface used by the model. The policy and arithmetic in this demo are scripted, not learned. Running it repeatedly appends memory entries; it does not deduplicate them.

`trace.json` contains generated bytes, operation results, and memory-commit events. **Traces are private host diagnostics:** they can contain sensitive content and are not automatically shared with streams.

### 2. Train a multi-stream attention smoke test

```sh
cargo run --release -- train 12000 checkpoint.json
```

Each stream receives a private `A`/`B` bit. After scripted publication, the model predicts the **other stream's bit** for both streams in one forward pass. All four input combinations are used during training and evaluation. The command reports loss, accuracy out of eight stream predictions, and a publication-disabled ablation.

This tests learned use of peer information, **not learned publishing, generalization, or autonomous collaboration**. A longer budget is intentional: a short run can learn the output alphabet while staying at chance on the actual task. The checkpoint from this command is not trained to generate JSON operations.

The extended regression test also flips only peer-publication content while holding private input fixed, and separately masks peer-publication attention:

```sh
cargo test --release --test learning -- --ignored
```

### 3. Train operation generation from demonstrations

```sh
cargo run --release -- train-trace examples/collaboration-dataset.json 10 checkpoint.json
```

The dataset is a JSON array of episodes. An episode contains:

- `scope`: the fixed application memory namespace;
- `working`: one list of initial working entries per stream;
- `memory`: optional seed memory drafts;
- `rounds`: groups of stream operations whose frames begin together.

See [examples/collaboration-dataset.json](examples/collaboration-dataset.json) for publishing, proposing and accepting an edit, selecting memory, and finishing.

The trainer serializes each operation as a JSON line and teacher-forces the next byte for every participating stream. Shorter frames wait while other streams complete theirs. Every demonstration is replayed and context-checked before training; invalid actions are not silently used as successful targets. Loss is averaged per supervised byte, not per action.

To reuse a distilled student, pass its checkpoint as the fourth argument: `train-trace DATASET EPOCHS OUTPUT_CHECKPOINT INITIAL_CHECKPOINT`. Without it, this command initializes a new student.

The example is one tiny demonstration, not an adequate agent-training corpus. Low teacher-forced loss does not imply that free-running generation will produce valid operations or solve a task. Numerical training failure can occur after earlier successful updates; an entire training episode is not an optimizer transaction.

### 4. Run a checkpoint without teacher forcing

```sh
cargo run --release -- run checkpoint.json examples/finish-episode.json 256 memory.json
```

`run` takes **one episode object**, unlike `train-trace`, which takes an array. It uses only the episode's initial state; demonstration `rounds` are ignored. The finish example demonstrates the input schema, not a promise that a checkpoint trained on arithmetic will solve it.

Each decoding round computes all active distributions from the same snapshot, greedily selects one byte per stream, and applies completed operations at the boundary. Malformed operations are rejected and fed back to the originating stream. Generation stops when all streams finish or the round limit is reached.

The optional memory file is loaded before the task and saved after a successful task-boundary commit. Without it, committed memory remains in RAM. An unfinished task never saves staged memory. Episode seed memories are appended even when a file is loaded; omit them when they should not be reinserted. JSON diagnostic events go to standard output; status goes to standard error.

### Neural computation

The default model has width 16, one attention head, one decoder layer, and a width-32 tanh feed-forward network. It has residual connections, a 257-symbol vocabulary (256 bytes plus input-only BOS), and trainable token, position, stream, and context-kind embeddings. Every parameter group is trained by analytic backpropagation. Finite-difference tests check gradients across all groups.

A single model input contains query positions for every active stream. Attention selects authorized working, history, publication, inbox, and retrieved-memory tokens. Peer histories are private; only explicit publications are shared. Positions advance across entries within a reader/source/type window, preserving entry/content association. Publication source identity is structural, rather than inferred from a prose envelope.

The reference encoder duplicates shared payloads per reader to preserve reader-local positions and avoid hidden-message lengths affecting visible positions. Invisible publications with no active readers are skipped. Dense masks and duplication are intentionally correctness-first, not scalable attention implementations.

Only the requested query rows are evaluated by the single layer. Other mask rows are identity rows. **Stacking layers requires redesigning these masks and contextual representations**, not merely repeating the current layer. All state is re-encoded every round, so context edits cannot leave stale KV-cache entries.

Default CLI context limits are 2,048 encoded tokens, up to 256 recent history bytes per stream, and 512 positions per reader/source/type window. Full generated history remains in the engine, up to its separate byte limit. Non-history context overflow is an explicit error, not silent truncation. These limits and ablations are configurable through the library.

### Collaboration protocol

Operations are newline-delimited UTF-8 JSON. For example:

```json
{"op":"publish","target":null,"content":"a = 17"}
{"op":"propose_edit","target":1,"entry_id":2,"expected_version":1,"replacement":"total = 42"}
{"op":"accept_edit","proposal_id":1}
{"op":"memory_propose","content":"17 + 25 = 42","kind":"fact","source_references":["checked arithmetic fixture"]}
{"op":"finish","result":"42"}
```

Also supported: `reject_edit`, `memory_query`, and `memory_revise`. The full typed schema is `state::Operation`. Ordinary bytes accumulate locally; only complete valid frames execute. Oversized frames are discarded through the next newline. This is a byte-level tokenizer, so non-ASCII characters take multiple decoding rounds.

- All eligibility checks use the committed snapshot from the start of the round.
- An edit proposal cannot be accepted in the same round in which it is created.
- Only the target can accept or reject a peer edit.
- Accepting an edit appends a working-entry version; previous content and generation history remain available to the host.
- Stale versions fail explicitly. Valid operations commit in ascending stream-ID order.
- The application fixes stream count and memory scope. Generated fields cannot change those policies.

### Durable memory

Memory selection is explicit: `memory_propose` and `memory_revise` stage changes. Once **all streams finish**, `Engine::commit_memory` applies the staged batch atomically in RAM. `MemoryStore::save` makes it durable; the engine never silently writes to disk.

Memory entries retain kind, scope, provenance, ID, version, and status. Retrieval uses deterministic case-insensitive word overlap in the exact authorized scope, with entry and byte limits. Storage budgets charge UTF-8 content bytes across **all retained versions**, including superseded and retracted versions; metadata and JSON overhead are not charged.

The store writes an exclusive same-directory temporary file, syncs it, and renames it over the destination. On Unix it also syncs the directory. It assumes **one writer per file**; it is not a concurrent database. Corrupt or incompatible files are rejected rather than repaired or overwritten by the memory store. Model checkpoints use a separate JSON format and ordinary non-atomic file writes.

`revise`, `retract`, and `forget` are available through the memory library. `forget` removes all retained versions from this store, but cannot erase traces, other process copies, snapshots, or backups. No secure storage erasure is provided. Scope checks and provenance validation are mechanical controls, **not factual verification or a complete defense against prompt injection**.

## Validation

```sh
cargo fmt --all -- --check
cargo test
cargo clippy --all-targets -- -D warnings
cargo test --release --test learning -- --ignored
```

Tests cover gradients, masked-token noninterference, learning, checkpoint roundtrips, snapshot visibility, stale edits, owner permissions, invalid byte frames, budgets, memory scopes, corruption, durable reload, deletion, and executable teacher forcing.

## Research work still ahead

- Held-out tasks, external message-passing and single-stream baselines, compute/latency comparisons, and multi-seed statistical evaluation.
- Larger and more diverse demonstrations; free-running operation accuracy and task success evaluation.
- Outcome-based optimization of communication and memory utility.
- Learned retrieval/routing, dynamic stream counts, asynchronous scheduling, and latent memory.
- Efficient sparse attention, tensor kernels, GPU execution, and cache-aware mutable context encoders.
- Stronger trust policies and externally verified memory commits.

Simultaneous output distributions do not imply multithreaded execution or a measured speedup. This implementation is a foundation for testing the design's hypotheses, not evidence that they are already true.
