# Rust performance audit

Generated artifacts under `docs/performance/data/` are intentionally ignored by Git and remain local. This report retains the aggregate findings; the reproduction commands regenerate raw samples, profiles, logs, and instruction evidence on a fresh checkout.

## 1. Executive summary

Audited on 2026-10-26 against production revision `5bfef5f1fa05101728437b619fc17470016b4755`.

Four focused, safe-Rust production changes were retained:

1. **Remove full-engine cloning from byte/action rounds**, while retaining snapshot authorization and transactional round-level errors.
2. **Store one reader ID per encoded token**, rather than allocating a one-element vector per token.
3. **Separate the matrix backward reduction from independent weight updates**, allowing LLVM to vectorize updates without changing floating-point addition order.
4. **Score memory overlap without building an owned word set per entry**, preserving Unicode normalization, distinct-word relevance, ranking, scope, and result budgets.

The repeated, controlled comparison measured:

- **In-memory example episode training: 153.85 → 68.06 ms, 2.26× faster** (55.8% less latency).
- **Complete one-epoch student distillation fixture, including initial/final evaluation: 2.548 → 1.677 ms, 1.52× faster**.
- **4,096-entry retrieval: 1.409 → 0.663 ms, 2.13× faster**.
- **Training steps: approximately 2.05–2.18× faster** across the context-size matrix.
- A synthetic 4,096-round framing replay improves **568.68×**, but this deliberately excludes context encoding and neural computation. It is not an application-wide speedup.

No public APIs, checkpoint formats, persistence formats, default feature flags, or release profile settings changed. No production `unsafe`, handwritten SIMD, GPU code, new production dependency, or production parallelism was introduced. Criterion is a development dependency. Benchmark orchestration/reporting is compiled Rust; there are no scripting-language files added by this audit.

## 2. Architecture, workloads, and requirements

### Execution paths

| Path | Main stages | Performance character |
|---|---|---|
| Student decoding | `context::encode` → `TinyTransformer::predict` → byte framing/action application | CPU and allocation intensive; repeated for each generated byte |
| Trace training | Full validation replay → second replay with one SGD update per supervised byte | Neural computation plus context allocation and engine bookkeeping |
| Student distillation | Answer-input construction → initial evaluation → byte-wise SGD → final evaluation | CPU-bound kernels and repeated causal-mask construction |
| Durable memory | Scoped lexical query; version retention; staged task-boundary commit; JSON save/sync | Allocation/comparison costs in retrieval; explicit filesystem I/O on save |
| GGUF teachers | Optional llama.cpp backend or loopback HTTP; prompt prefill and autoregressive generation | External inference/device costs, plus blocking transport for HTTP |

This is one Cargo package, not a multi-crate workspace. Default dependencies are `serde` and `serde_json`. Default features are empty. The optional Cargo feature `native` enables the Linux C bridge and requires external compatible llama.cpp libraries through `LLAMA_CPP_DIR`.

The default student has width 16, one attention head/layer, a width-32 tanh FFN, and a 257-symbol byte/BOS vocabulary. The benchmark configuration has 18,913 f32 parameters (75,652 bytes). Encoding duplicates shared content per reader to preserve reader-local positions and privacy. `ModelInput::visible` is a public dense `Vec<Vec<bool>>`; only requested query rows are evaluated by the single layer.

The protocol is deterministic: all eligibility checks use the old snapshot, valid actions apply in ascending stream order, and malformed operations are feedback outcomes. Actor/history/round failures must leave a byte round unchanged. Pending memory stays invisible until all streams finish. These requirements take priority over speed.

### Representative inputs

- Two-stream fixtures with 16/96/256-byte working entries and a publication: **105 / 425 / 1,065 encoded tokens**, two query rows, width 16. Publication notices are included.
- Additional complete prediction rounds with **1, 2, 4, and 8 streams** and 32-byte entries/publications.
- Byte framing replay at **64 / 512 / 4,096 rounds**, two bytes per round, bounded histories. This isolates growing-history/trace overhead; it is not a model benchmark.
- The actual `examples/collaboration-dataset.json` episode, including publication, peer edit, memory staging, and finish. Validation and training use the production replay paths. The training measurement includes model initialization and preflight validation.
- Answer-only distillation of a deterministic 21-byte response, including both evaluation passes and one training epoch. No teacher/model download or network call is part of this fixture.
- Memory stores with **16 / 256 / 4,096 entries**, 75% in the authorized scope, Unicode content, duplicate query words, a missing query term, tied relevance scores, and entry/byte result limits.
- Concurrent independent medium-context requests using prestarted scoped workers at **1 / 2 / 4 / 8 / 16 workers**, 32 predictions per worker per timed operation. Barrier synchronization is included; thread creation is excluded.

No numerical latency/throughput SLA exists in the repository. The practical goals are lower byte-round latency, greater training/retrieval throughput, less allocation traffic, and scaling within the documented 2,048-token context limit. Larger model widths, production teacher traffic, long heterogeneous corpora, startup, checkpoint serialization, durable filesystem latency, and native teacher execution are **not** characterized by these measurements.

### Initial hypotheses

- Re-encoding and dense masks may dominate sufficiently large byte-decoding contexts.
- Cloning a growing engine each round may make cumulative replay costs quadratic.
- Small matrix kernels may be limited by loop structure, bounds checks, and serial reductions rather than raw FLOP throughput.
- Retrieval may spend excessive work allocating word sets rather than scoring matches.
- Per-query threading and GPU dispatch may cost more than these small serial operations warrant.

These hypotheses were tested with stage benchmarks, allocation accounting, differential tests, and disassembly—not accepted from static inspection alone.

## 3. Baseline environment and methodology

### Hardware and compiler

- AMD Ryzen 7 7435HS: 8 physical cores, 16 logical processors, SMT enabled.
- Per-core caches: 32 KiB L1d and 512 KiB L2; shared 16 MiB L3.
- Linux `6.18.58_1`, x86-64, one NUMA node.
- `rustc 1.99.1 (58cf8f9c3 2026-10-13)`, LLVM 23.1.1; Cargo 1.99.1.
- Cargo release/bench configuration: optimization level 3, repository `debug = 1`, default codegen-unit/LTO settings, default x86-64 CPU target, no `RUSTFLAGS`, no Cargo features enabled. The default codegen-unit setting is 16; no LTO override was used in the primary comparison.
- Primary runs pinned to CPU 0. Scaling runs allowed CPUs 0–15.
- CPU governor was `powersave`; boost was enabled. Frequency, temperature, host background activity, and cache residency were not externally controlled.

Environment snapshots, raw samples, estimates, and process resources are under [`data/`](data/).

### Criterion configuration

`benches/performance.rs` uses **Criterion 0.8.2**, 30 flat samples, 300 ms warmup, a 1-second requested measurement period, 10,000 bootstrap resamples, and a 3% practical noise threshold. Slow operations necessarily exceed the requested measurement period to collect 30 samples. Results below are **Criterion mean estimates**, not medians. `std::hint::black_box` protects inputs/results.

Training-step benchmarks clone a fixed seeded model with `iter_batched_ref`; setup/destruction are excluded while the production SGD operation is timed. Full-episode/distillation benchmarks initialize their own deterministic model within the timed operation. This avoids benchmarking different trained weight distributions as calibration/iteration counts change.

A separate allocation probe runs each operation once with accounting enabled. It counts allocation/reallocation calls and requested bytes, including zeroed allocations. Bytes are **cumulative allocation traffic**, not live memory, bytes copied, or RSS. Setup outside an operation is excluded. Reallocation counts charge the new requested size. The benchmark-only `GlobalAlloc` implementation forwards pointers/layouts directly to `System`; its safety invariant is documented. Accounting is disabled during timed samples, but the allocator's disabled-mode flag check remains in both binaries.

Synthetic cache-eviction measurements touch a 32 MiB buffer at 64-byte strides **outside** the timed prediction using Criterion per-iteration batched setup. This measures an eviction-stressed model call, not a guaranteed cold-cache state, cold process startup, cold filesystem cache, or a hardware cache-miss count.

### Baseline preservation and repeat policy

[`original.json`](data/original.json) preserves the first Criterion baseline collected before production optimization. Intermediate experiments are preserved as `state.json`, `readers.json`, `mask.json`, `kernel.json`, and `retrieval.json`.

The finalized harness was then built against an isolated copy of the original revision and the optimized sources. The same harness, fixtures, dependencies, compiler, flags, and affinity were used for both. The four full runs were serial, in **A–B–B–A** order:

1. `baseline-final.json`
2. `optimized-final.json`
3. `optimized-repeat.json`
4. `baseline-repeat.json`

The main table uses the repeat pair. Some first-pair medium-context and large-allocation measurements drifted substantially, including an apparent prediction improvement that disappeared on repetition. Those are **not** attributed to the optimization. Bootstrap confidence intervals describe within-run variation and do not eliminate across-run thermal, allocator-state, frequency, or scheduling effects.

### Profiling limitations

- `perf`, Valgrind/Callgrind/Cachegrind, heaptrack, and flamegraph tooling were unavailable.
- A hardware-cycle `perf_event_open` probe returned `EACCES`; `/proc/sys/kernel/perf_event_paranoid` was 2.
- GDB was installed, but launching a traced child failed with `ptrace: Operation not permitted` in the sandbox.
- Consequently **cycles/op, IPC, retired instructions, branch misses, L1/L2/LLC misses, TLB misses, pipeline stalls, sampled function CPU percentages, and memory bandwidth were not measured**. No such values are inferred as measurements.
- `objdump` supplied instruction-level evidence. Criterion stage timings and direct allocation counts supplied the hotspot evidence available here. This is not a substitute for a complete sampled call graph on an unrestricted deployment host.

## 4. Bottleneck evidence and implemented changes

### 4.1 Full-engine cloning — `src/state.rs`

**Evidence:** Original `step_tokens` cloned the engine, then `step_actions` cloned it twice again. Clones included growing histories, frames, audit trace, working versions, proposals, and memory. The 4,096-round replay requested **10,273,700,428 bytes** over **262,178 allocations**. Original latency growth was much faster than input growth.

**Solution:** Preflight actors, all participating histories, and round overflow before byte mutation. For actions, retain all validation results from the old snapshot before applying any action; then apply in sorted order. Operation rejections remain outcomes, not round-level errors. No full engine clone is required.

**Measured:** Repeat replay latency **205,353.01 → 361.11 µs** (204,991.90 µs saved, 99.8% less latency). Cumulative requested bytes fall to **4,525,846**, with **8,267 allocations**. The smaller replay cases confirm approximately linear growth after optimization at fixed stream count. Isolating this change improved the initial complete training episode by only **2.9%**: it was a real framing bottleneck, not the dominant cost of neural training.

**Risk/validation:** A test-only copy of the original algorithms compares full engine state, reports, errors, notices, and traces after every transition. Five differential tests cover arbitrary/invalid bytes, complete collaboration, frame discard/recovery, actor errors, history exhaustion including the second actor, round overflow, snapshot edit semantics, and ordered conflicts. Existing protocol/memory tests also pass.

### 4.2 Per-token reader allocations — `src/context.rs`

**Evidence:** Private `Builder::block` required exactly one reader yet cloned a `Vec<StreamId>` into every token. At 1,065 tokens, encoding used **2,166 allocation calls**.

**Solution:** Represent that private invariant with one `StreamId`, and compare IDs directly when filling query masks. Public token ordering, reader-local positions, visibility matrices, and budgets are unchanged.

**Measured:** Small encoding **6.05 → 3.81 µs**, medium **69.79 → 48.62 µs**, large **579.58 → 560.17 µs** in the repeat comparison. Large allocation calls fall **2,166 → 1,094**; requested bytes fall **1,398,537 → 1,324,489**. The isolated experiment improved initial example validation **9.35 → 5.30 ms** after the engine change.

**Remaining bottleneck:** The 1,065-token mask alone has 1,134,225 boolean payload bytes, plus row headers/allocations. Encoding remains ~560 µs versus ~805 µs for a complete large prediction round. These separate timings are useful scale indicators, **not additive profiler shares**. A query-row or sparse mask needs a deliberate public API migration; it was not smuggled into this patch.

### 4.3 Backward matrix kernel — `src/model.rs::linear_backward`

**Evidence:** Initial small/medium/large training steps cost roughly **143 / 451 / 1,091 µs**. Original disassembly contains scalar `mulss`/`addss`, two per-element bounds-check branches, and a load/store of the input accumulator in the inner loop. See [`backward-before.asm`](data/backward-before.asm).

**Solution:** Borrow a checked matrix row, accumulate the input gradient in its original addition order, then separately update the independent weight-gradient elements. No reassociation, FMA substitution, unsafe indexing, extra buffer, or hand-written SIMD is needed.

**Measured:** Repeat training steps **142.84 → 69.84**, **448.72 → 205.84**, and **1,101.60 → 518.34 µs**. The complete example episode improves **153.85 → 68.06 ms**, including preflight and replay. Parameter/activation allocation sizes are unchanged by this kernel change.

**Instruction evidence:** [`backward-after.asm`](data/backward-after.asm) has packed `mulps`/`addps` weight updates and a register-held, unrolled scalar reduction. Row-level bounds checks remain. This establishes generated vectorization and a different loop structure; it does **not** establish measured IPC or branch-miss improvements.

**Validation:** A new bit-for-bit comparison against the original scalar kernel covers multiple row counts, scalar/tail widths, width 16/32, and vocabulary width 257, including nonzero starting gradients. Finite-difference checks across every parameter group, normalized predictions, overflow rejection, checkpoint continuation, and learning tests pass in optimized builds.

### 4.4 Temporary retrieval word sets — `src/memory.rs::MemoryStore::query`

**Evidence:** The original query lowercased every entry, allocated every word, built an entry `BTreeSet`, and intersected it with the query set. At 4,096 stored entries, one query requested **2,078,077 bytes over 33,827 allocation calls**.

**Solution:** Keep sorted distinct query words, lowercase each entry exactly as before, binary-search borrowed word slices, and track distinct hits by entry ID in one query-sized vector. The per-entry word strings/tree are eliminated. Full ranking, ascending-ID ties, and oversized-match skipping are unchanged. No persistent index/cache requires synchronization with revisions or forgetting.

**Measured:** **1,409.05 → 662.86 µs**, saving **746.19 µs** (53.0% less latency). Allocation calls fall **33,827 → 3,109**; requested bytes fall **2,078,077 → 241,973**. Small and medium stores also improve.

**Validation:** Differential reference tests cover repeated words, Greek contextual casing, dotted I, accented Latin, Japanese, punctuation/empty queries, revisions, retractions, deletion, result limits, and byte budgets. Existing scope, persistence, and ranking tests remain unchanged and pass.

## 6. Parallelism and scaling

No production threading was added. These are independent immutable-model requests, not parallel attention or parallel SGD. The full CPU-0 matrix includes 1/2/4/8/16 workers as a single-core scheduling control: throughput remains approximately flat, as expected.

With affinity expanded to CPUs 0–15, the optimized independent-request experiment measured:

| Workers | Batch latency µs | Forward calls per batch | Approx. forward calls/s | Throughput scaling vs 1 worker |
|---|---:|---:|---:|---:|
| 1 | 2,066.30 | 32 | 15,487 | 1.00× |
| 2 | 2,060.99 | 64 | 31,053 | 2.01× |
| 4 | 2,203.06 | 128 | 58,101 | 3.75× |
| 8 | 3,473.50 | 256 | 73,701 | 4.76× |
| 16 | 5,872.32 | 512 | 87,189 | 5.63× |

Scaling samples have CVs **2.2–8.2%**; baseline scaling is similar. Moving from 8 to 16 workers gives only about 18% additional throughput, while doubling workers and worsening batch latency. SMT, reduced all-core boost, synchronization, allocator behavior, and scheduling are plausible contributors, but were not isolated. The whole scaling suite used ~4.5 CPU-seconds per wall-second on average; CPU saturation is not equivalent to useful scaling.

Amdahl's law cautions against expecting linear speedup from parallelizing a single small query: encoding, staging, and output selection remain serial, and coordination adds work. These independent-request results cannot identify a true serial fraction for one model call. A persistent outer request pool is the plausible first concurrency extension; deterministic byte-round ordering and sequential SGD updates must remain intact.

## 7. Rejected experiments and optional acceleration

### Independent zero-initialized mask rows — rejected and reverted

Replacing cloned dense mask rows with independently zero-initialized rows looked attractive for avoiding repeated copies. After the reader change, medium encoding regressed **49.38 → 63.77 µs** (~29%), validation regressed **5.30 → 5.64 ms**, and episode training did not improve. Large encoding improved only ~1.4%. Allocator/zeroing behavior did not support the hypothesis. Production retains the original dense-mask construction. Raw data: `readers.json` versus `mask.json`.

### CPU-native targeting — not adopted

An exploratory separate build used **`-C target-cpu=native`**, without enabling the Cargo `native` teacher feature. Relative to the optimized repeat, episode training was **68.06 → 72.13 ms**, small training **69.84 → 72.36 µs**, and large training **518.34 → 513.26 µs**. No consistent end-to-end benefit justified hardware-specific deployment requirements. This was one exploratory run, not a precise cross-run regression estimate. The portable release target remains unchanged.

### Thin LTO and one codegen unit — not adopted globally

An exploratory build used **`CARGO_PROFILE_RELEASE_LTO=thin`** and **`CARGO_PROFILE_RELEASE_CODEGEN_UNITS=1`**. Small prediction improved **20.22 → 18.99 µs**, medium **62.22 → 58.97 µs**, and large **187.54 → 181.02 µs**. However episode training measured **73.36 ms** versus **68.06 ms**, and small training was slower. A specialized inference-only deployment could revisit this tradeoff, but a global profile change is not justified by the mixed result. Raw data: `cpu-native.json`, `thin-lto.json`.

### GPU feasibility

`nvidia-smi` existed but could not communicate with the NVIDIA driver. Native teacher libraries/model execution were not configured for this audit. No GPU timing, transfer timing, or kernel prototype was possible or claimed.

The student has very small matrices, byte-wise serial dependencies, CPU-built mutable contexts, and a large host-side mask cost. There is no demonstrated GPU workload here that justifies adding `wgpu` or accelerator-specific code. A batched, larger-width student with GPU-resident weights/contexts would be a different project. Frozen GGUF teacher offload already belongs in llama.cpp; preserve its hybrid recurrent-state reset semantics and validate drivers/ABI separately.

PGO, manual SIMD, alternate allocators, arenas, SoA rewrites, and lock-free structures were not implemented: the retained changes delivered large gains without that maintenance/correctness burden, and measurements did not justify further specialization.

## 8. Prioritized remaining opportunities

Implemented impacts below are measured; unimplemented impacts are explicitly hypotheses, not forecasts with invented percentages.

| Priority | Location | Bottleneck | Proposed optimization | Expected impact | Complexity | Confidence |
|---|---|---|---|---|---|---|

Mutable KV caching and stacked layers require architectural visibility work, not a simple cache insertion.

## 10. Reproduction — compiled Rust and native tools only

All commands below are direct executable invocations, with no shell automation, substitutions, environment-assignment syntax, or scripting-language dependency. Run from the repository root on Linux. `taskset`, `getconf`, Git, and Rust/Cargo are required. First dependency fetch needs network access; subsequent builds use the lockfile offline. Existing result names are protected from overwrite; choose new names for further runs.

### Build the Rust utility and recreate the original production baseline

In a fresh checkout containing this audit's changes, with no pre-existing `target/performance/original-project`:

```text
cargo fetch --locked
cargo build --release --locked --offline --example performance_results
cargo run --release --locked --offline --example performance_results -- prepare-baseline 5bfef5f1fa05101728437b619fc17470016b4755
cargo run --release --locked --offline --example performance_results -- build baseline
cargo run --release --locked --offline --example performance_results -- build optimized
```

`prepare-baseline` uses read-only Git commands to copy the original revision into `target/`, then installs the identical current Cargo lockfile and Criterion harness. It never checks out, rewrites, or resets the working tree. It refuses to overwrite an existing baseline source directory. `build` discovers Cargo's actual emitted executable from JSON messages and copies it to a stable name.

### Reproduce serial A–B–B–A measurements

```text
cargo run --release --locked --offline --example performance_results -- run target/performance/baseline-bench repro-a1 0
cargo run --release --locked --offline --example performance_results -- run target/performance/optimized-bench repro-b1 0
cargo run --release --locked --offline --example performance_results -- run target/performance/optimized-bench repro-b2 0
cargo run --release --locked --offline --example performance_results -- run target/performance/baseline-bench repro-a2 0
cargo run --release --locked --offline --example performance_results -- compare docs/performance/data/repro-a2.json docs/performance/data/repro-b2.json
cargo run --release --locked --offline --example performance_results -- describe docs/performance/data/repro-b2.json
```

Each `run` archives Criterion estimates and raw samples, a complete log, disabled-accounting timing measurements, a separate allocation-only probe, process peak RSS/CPU times from `/proc`, and environment metadata. Do not run builds, tests, or other benchmark processes concurrently with timed runs. Repeat on deployment hardware with controlled power/temperature if small differences matter.

### Scaling and optional code-generation experiments

```text
cargo run --release --locked --offline --example performance_results -- run target/performance/baseline-bench repro-scale-a 0-15 concurrent
cargo run --release --locked --offline --example performance_results -- run target/performance/optimized-bench repro-scale-b 0-15 concurrent
cargo run --release --locked --offline --example performance_results -- build native
cargo run --release --locked --offline --example performance_results -- run target/performance/native-bench repro-native 0
cargo run --release --locked --offline --example performance_results -- build thin-lto
cargo run --release --locked --offline --example performance_results -- run target/performance/thin-lto-bench repro-lto 0
```

Here `build native` means CPU-native **compiler targeting**, not the Cargo `native` teacher feature. The Rust utility supplies the actual compiler/profile environment directly to Cargo and records build metadata next to the executable. No hardware-specific setting is enabled by default.

### Inspect instructions and, on a suitably provisioned host, profile counters

```text
objdump -Cd target/performance/baseline-bench
objdump -Cd target/performance/optimized-bench
perf stat -e cycles,instructions,branches,branch-misses,cache-references,cache-misses taskset -c 0 target/performance/optimized-bench --bench --profile-time 10 predict/large
perf record -g taskset -c 0 target/performance/optimized-bench --bench --profile-time 10 train_episode
perf report --stdio
```

The `perf` commands are **follow-up instructions**, not commands that succeeded in this environment. Restrict counters to those supported by the host and account for multiplexing. Sample call stacks before making additional layout, branchless, caching, GPU, or parallel-kernel changes.

### Artifact map

- `original.json`: first pre-optimization Criterion baseline.
- `state.json`, `readers.json`, `kernel.json`, `retrieval.json`: successive targeted experiments.
- `mask.json`: rejected mask-construction experiment.
- `baseline-final.json`, `optimized-final.json`, `optimized-repeat.json`, `baseline-repeat.json`: finalized-harness full comparisons.
- `*-scaling-final.json`: independent-request scaling comparisons.
- `cpu-native.json`, `thin-lto.json`: optional code-generation experiments, not defaults.
- `allocations-*.jsonl`: separate allocation profiles, not timed samples.
- `resources-*.json`, `environment-*.json`/`.txt`, and `*.log`: reproducibility context.
- `backward-before.asm`, `backward-after.asm`: instruction evidence for the retained kernel change.

Binaries, full disassembly, Cargo build products, and the original-source build copy remain under ignored `target/performance/`; they are not production source or required committed artifacts.
